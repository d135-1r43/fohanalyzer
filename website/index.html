What it does

Everything you reach for at front of house

What you press sits in a strip above the plot, what you read sits in the rail beside it, and what you set once lives in Preferences.

Two traces, one plot

The measurement-mic trace sits over the console solo-bus trace, so room response and source signal are read against each other rather than in turn. A solo trim closes the 10–20 dB the console leaves between them, and Match lines up the averages in one click.

A spectrograph beside the RTA

A scrolling time × frequency view on the same axis as the RTA, under it or on its own. It shows what built up over the last 10, 30 or 60 seconds, so a ring that comes and goes leaves a stripe instead of a moment you missed.

Ring-out assist

Detect ring runs pitch detection over the live mic and reports the actual ringing fundamental — not the band centre a peak marker rounds to — then suggests a cut. Four blocks are estimated independently and the median wins, so one glitched block cannot move the notch.

SPL with a memory

Calibrate once against a known reference level and the meter reads genuine dB SPL: the Leq over a window from 10 seconds to an hour, the Fast level, and the maximum and peak since a reset. Every second of the show is logged to a CSV you can hand to whoever asks what the level was.

Hold the venue limit

Set the limit once per gig, e.g. 98 dB LZeq over 15 minutes. The Leq turns amber within 3 dB of it and red above it, and the rail counts the time spent over and draws the last 30 minutes against the line.

Overlays that answer questions

Peak hold for what the plot did while you were not looking, peak markers for where it lives, and a transfer function for the mic−solo difference.

Reference capture

A dashed ghost of both traces, frozen where you left them. The honest way to A/B before against after EQ, instead of trusting what you remember the curve looked like.

1/1 to 1/24 octave

Wide bands to see the shape of a room, narrow bands to find the one that is about to go. Smoothing and frame averaging on top of either.

Works with nothing plugged in

Every source can run from a simulated preset, so the whole app is usable — and reviewable, and testable — without an interface on the desk.

It remembers your rig

Inputs, channels and view options persist between launches, and each interface and channel keeps its own SPL calibration, so a new rig never reads with the last one's offset. A missing interface quietly falls back to the simulator instead of pointing at a line that cannot open.

Ask an AI assistant

An optional, read-only MCP server lets Claude Code, Claude Desktop or ChatGPT read the ring-out history, the readouts and the current band levels, and turn them into mixing tips. It is off by default and only answers on this machine.

Open source

Free as in freedom, and free as in it costs nothing

FOHanalyzer is licensed GPL-3.0-or-later. You can read every line, build it yourself, change what annoys you, and pass it on. There is no paid tier waiting behind a feature, because there is no tier.

The licence is not a marketing position — it is inherited. TarsosDSP, which does the FFT and the pitch detection, is GPL-3.0, and linking against it means everything shipped here has to be GPL-compatible too. That suits the project fine.

How to contribute Read the licence
Runtime dependencies 5 JavaFX, TarsosDSP, SLF4J, and the MCP SDK on Jetty. That is the whole list.
Network calls 0 No account, no licence check, no telemetry, no update ping. The MCP server only listens.
Config files 0 Settings live in the platform preference store, not a dotfile you have to find.
CI on every push ✓ Tests, format check and a packaged .dmg attached to the run.

Your measurements stay on your laptop

The app captures audio from a local input, draws it, and forgets it. Nothing is uploaded, nothing is stored beyond the settings you chose, and the microphone permission macOS asks for is exactly what it says: the measurement mic and console feeds the analyser needs to read. You do not have to take that on trust — it is a few hundred lines you can read.

How it works

A small codebase, on purpose

Six packages, plainly named. If you have written any Java, you can find your way around this in an afternoon — which is rather the point of asking you to contribute.

Packages

PackageResponsibility
engineFrequency math, note names, formatting, signal simulation
dspPer-band averaging, smoothing, peak hold, stats, Leq, the SPL limit, spectrogram history
audioJava Sound capture, FFT and pitch detection, device enumeration
uiJavaFX canvas rendering and render loop, spectrograph, app shell, action strip, control rail, preferences
mcpAnalyzer history, MCP tools, and the embedded HTTP server that serves them
ui.controlsToggle, Segmented, Trim, Meter, LimitBar, LeqTrend, SourceCard, ChannelSelect, Logo

Live input is captured on a daemon thread into a 16384-sample ring buffer. Each frame the newest window is Blackman-windowed, transformed, and converted to dBFS per bin. The full write-up — including why the app is deliberately non-modular, and why the broadband RMS stays hand-rolled — is in the README.

A worked example: see, set, do

Every readout and control has one home, chosen by what you do with it. The rail on the right only shows: each level once, the SPL meter, the logged rings, and what the plot is computed with. Everything that is a setting — inputs, solo trim, calibration, display and analysis options — lives in Preferences, one page per area. And what you press during a show, from the view to Detect ring, sits in a strip right above the plot it acts on.

Nothing in Preferences is a commit step. The controls bind straight to the shared state that gets persisted anyway, so there is nothing to apply and nothing to cancel — the button in the corner only closes the window, and closing it changes nothing. The rail still names what each setting is, as text — trim −3.5 dB, LZeq · 5 min — because "what is this trace, and what is it computed with" is a question you ask at a glance while working, even though the answer is only set once.

That is the level at which the whole codebase is documented, which is what makes it approachable to change.

Contribute

This is where you come in

FOHanalyzer gets better the more rigs it meets. You do not need to be a DSP engineer to move it forward — some of the most useful contributions are not code at all.

Run it on your rig and tell us what broke

Device enumeration is the messiest part of any audio app. An 18-in Scarlett, a Wing, a USB stick mic, a Dante virtual soundcard — each one is a data point nobody has unless you send it.

Open an issue →

Package it for Windows and Linux

The code is plain JavaFX and Java Sound; only the packaging script is macOS-specific. A well-scoped, high-impact job with a clear finish line — and one of the most-asked-for things in the project.

See what is involved →

Sharpen the measurement

A/C weighting, coherence, phase, impulse response, a proper dual-FFT transfer function. The dsp and engine packages are pure, fully tested functions — the friendliest place in the codebase to land a change.

Pick something up →

Argue with the interface

The rail shows, Preferences sets, and the strip above the plot acts. If something you need mid-show ended up in the wrong place for how you work, that is a real bug, and saying so is a real contribution.

A short guide to ringing out a wedge with this tool would help more engineers than most features would. So would a translation, or a screenshot of it working on your desk.

Two commands from clone to running

JDK 25 and Maven 3.9 are the only prerequisites, and the simulator means you can see the thing work before you own a measurement mic. 

$ git clone https://github.com/d135-1r43/fohanalyzer
$ cd fohanalyzer && mvn javafx:run
